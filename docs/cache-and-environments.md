# 8단계: 저장 후 캐시 초기화와 기존 환경 유지

2026-10-20 사용자 결정 및 로컬 실행 기록입니다. 기존 구현을 재사용하며 운영 설정 변경·DB 이벤트 구독·새 캐시·폴링을 추가하지 않습니다.

## 공개 데이터 반영 계약

사용자는 두 앱 모두 실시간 갱신 서비스가 아니라고 확정했습니다. 관리자 저장 후 **이미 있는 서버 캐시만 무효화**하고 열린 화면은 자동 갱신하지 않습니다. 화면을 새로 열거나 새로고침해 실제 서버 조회가 발생할 때 최신 데이터를 읽습니다. 단순 곡 선택은 Loud가 이미 받은 카탈로그 안에서 이루어지므로 새 서버 조회가 아닙니다. Next의 기존 클라이언트 Router/prefetch 캐시까지 즉시 갱신한다고 보장하지 않습니다.

| 경로 | 기존 구조 | 현재 처리 |
| --- | --- | --- |
| Mono 공개 곡/원작/만화 목록 | `getPublicCatalog`, `use cache`, `public-catalog`, `cacheLife("hours")` | 공통 데이터 저장 성공 후 기존 태그 무효화 |
| Mono 곡별 가사 | `getLyricTrackByMusicId`, 같은 태그/수명 | 같은 무효화로 다음 서버 조회 시 재계산 |
| Mono 서적 구매 정보 | `getBookPurchaseInfoById`, 같은 태그/수명 | 같은 무효화 적용 |
| Mono 나머지 비캐시 조회·파일/독자 API | 기존 DB/R2 조회·접근 조건 | 새 캐시를 넣거나 파일 제공 정책을 바꾸지 않음 |
| Loud 카탈로그·추천 목록 | 홈 `connection()` 후 매 요청 DB 조회, 요청 간 데이터 캐시 없음 | 별도 무효화 요청·캐시 추가 없음 |
| 열린 공개 화면 | Loud가 mount/focus/카탈로그 storage 신호로 `router.refresh()` | 해당 훅/호출 제거. Mono에도 자동 갱신 추가 없음 |

정상 저장 경로:

1. 통합 관리자가 기존 트랜잭션/충돌 검사로 DB를 저장합니다.
2. Mono가 사용하는 공통 데이터라면 기존 서버 `refreshPublicCatalog`가 Mono의 `/api/internal/revalidate`에 알립니다.
3. Mono는 서버 전용 Bearer 비밀값과 고정 `scope: "catalog"`만 허용하고 `revalidateTag("public-catalog", { expire: 0 })`로 기존 캐시를 만료시킵니다. 임의 태그·경로를 받지 않습니다.
4. 다음 서버 요청은 캐시 miss로 최신 값을 읽습니다. 이 호출은 열린 브라우저에 새 데이터를 밀어 넣거나 플레이어를 재마운트하지 않습니다.

Loud 전용 콜·설정·추천 변경에는 Mono 알림도 필요 없습니다. 기존 `RefreshTarget`/관리자 scope 호환은 유지하며 Loud만 요청하면 `refresh: []`를 반환합니다. Loud의 사용하지 않는 internal/revalidate route와 공개 자동 갱신 훅은 제거했습니다. 옛 관리자 전용 storage marker는 9단계까지 남지만 공개 화면에서 이를 구독하지 않습니다.

DB 저장 성공과 Mono 알림 실패는 분리합니다. 비밀값 누락·타임아웃·HTTP 오류·성공 표식 없는 응답은 캐시 초기화 실패로 표시하며, 재시도는 DB를 다시 저장하지 않고 알림만 보냅니다. Loud 서버가 꺼져 있어도 캐시 알림 대상으로 접속하지 않습니다.

**직접 SQL·외부 도구로 DB를 수정한 경우:** DB 자체의 변경 이벤트를 자동 구독하지 않습니다. 해당 작업자가 보호된 Mono 무효화 API를 별도로 호출하거나 기존 캐시 만료를 기다려야 합니다. 새 DB 트리거/변경 로그/주기 확인 서비스는 만들지 않습니다.

## 로컬 상태 보존

- 재생 시간/재생 여부/seek·볼륨 저장·언어·테마/폰트·선택곡·사이드바/읽던 위치 코드는 변경하지 않습니다.
- DB 새로고침용 Loud `focus/storage` 구독만 제거했습니다. Mono 볼륨의 storage 구독과 Loud 재생 clock의 visibilitychange는 로컬 동작이므로 유지합니다.
- 공개 화면의 명시적 오류 재시도 버튼은 유지합니다. 로그인/관리자 편집/독자 인증의 `router.refresh()`까지 일괄 제거하지 않습니다.

## 환경 정책 — 사용자 후속 결정

사용자는 개발 환경에서 운영 DB를 연결해 사용하는 기존 방식에 익숙하며, 개발/프리뷰/운영 환경 분리를 고려하지 말고 기존 설정으로 적용하도록 확정했습니다. 앞서 보고한 분리 계획은 철회하며 8단계 완료 조건이나 9단계 선행 조건으로 두지 않습니다.

- 기존 DB/R2 연결을 그대로 사용하고 환경별 복제 DB·전용 버킷·분리 비밀값을 새로 요구하거나 만들지 않습니다.
- 후속 사용자 명시 요청으로 세 앱의 실제 DB 연결값을 원본과 같은 운영 Turso로 전환했습니다. 캐시 코드는 그대로 사용하고 합성 SQLite는 회귀 검사 자료로만 보존합니다.
- 앱별 캐시 알림 주소·비밀값 대응과 서버 전용 비밀값의 공개 방지 등 기존 연결 계약은 유지합니다. 배포 시 필요한 설정을 연결하되 별도 환경 분리를 다시 제안하지 않습니다.
- 합성 fixture 전용 회귀 검사는 계속 기존 로컬 파일에서 실행합니다. 이 검사의 자료 생성/복원 코드를 운영 DB에 실행하지 않습니다.

### 8단계 당시 로컬 상태 — 아래 후속 연결 기록으로 갱신됨

- 앱별 환경 파일 목록은 세 앱의 `.env.local`뿐입니다. 아래 결과는 실행 프로세스/배포 콘솔이 아닌 이 로컬 파일을 읽은 결과입니다. 세 앱 모두 같은 기존 합성 SQLite 파일을 참조하고 해당 파일이 존재합니다.
- 세 앱의 R2 인증값과 private/album 쓰기 버킷은 미설정입니다. 현재 로컬에서 실제 R2 업로드를 검증한 것으로 처리하지 않습니다.
- 관리자 Mono 알림 주소는 loopback이며 비밀값 쌍이 일치합니다. 기존 Loud 알림 환경값은 실제 파일에서 지우지 않았지만 이제 서버 코드에서 사용하지 않습니다.
- 공개 assets 주소로 읽는 것과 운영 R2 쓰기 권한을 갖는 것은 다릅니다. CDN 읽기 설정만으로 운영 DB/파일이 수정되지는 않습니다.
- Vercel 프로젝트/프리뷰 DB/R2 권한·실제 배포값은 아직 확인하지 않았습니다. 환경 분리 자체는 후속 사용자 결정으로 작업 범위에서 제외됐습니다.

## 검증과 남은 범위

- 기존 security 집중 검사에서 Mono의 정상/실패 응답, HTTP 오류, 누락 설정, Loud-only 무네트워크 및 mixed 요청의 Mono-only 알림을 확인했습니다.
- 기존 local-flow-check는 Mono endpoint의 무인증/잘못된 비밀값/범위 거부, 저장 필드 보존, 두 공개 앱의 다음 HTTP 조회 반영을 확인했습니다.
- 기존 editor/content HTTP 검사는 가사/콜·문서·추천 저장/충돌/권한을 회귀 검사했습니다. 합성 자료를 복원하며 기존 local-flow의 저장 시각 갱신 계약은 유지합니다.
- 실제 production cache 수명/배포 간 알림·브라우저 재생/볼륨 유지·기기별 QA·Vercel 연결은 미검증입니다. 개발 HTTP 성공을 production cache 검증으로 대신하지 않습니다.
- 빌드·푸시·배포·운영 DB/R2/DNS 변경은 실행하지 않습니다. 환경 계획 검토는 종료했으며 다음 작업은 사용자의 9단계 요청을 따릅니다.


## 후속: 운영 DB 연결 완료

사용자가 운영 DB 연결을 명시적으로 요청했습니다. 원본 Mono `.env`와 Loud `.env.local`의 DB URL/인증값이 같은 것을 확인하고, 세 앱의 무시된 `.env.local`에서 `TURSO_DATABASE_URL`/`TURSO_AUTH_TOKEN` 두 항목만 적용했습니다. 인증·공개 주소·R2 등 다른 환경값은 보존했습니다. 실제 비밀값은 출력/커밋하지 않았습니다.

- 세 로컬 서버를 같은 3100/3101/3102 포트로 재시작했습니다.
- 운영 DB 읽기 전용 트랜잭션으로 곡 36·가사 36·소설 38·만화 3·서적 3·Loud 설정 36·콜 문서 36건을 확인했습니다.
- Mono/Loud 홈 200과 알려진 운영 곡 표시, 인증된 관리자 목록 36곡/곡 ID 0 상세 200을 확인했습니다. 로그인 세션 발급 외에는 읽기만 수행했습니다.
- local-flow-check는 원격 DB 설정을 감지하면 요청 전에 중단하는 것을 확인했습니다. 합성 쓰기 회귀 검사는 실행하지 않았습니다.
- 연결 전 DB 두 설정의 복구 자료는 무시된 `.local/db-connection-before-production.json`에 있습니다. 되돌릴 때 각 앱의 두 DB 항목만 복원하고 서버를 재시작합니다. 전체 환경 파일을 덮어쓰지 않습니다.
- 운영 데이터·스키마·이미지 키 변경, migrate/seed, R2/DNS 변경, 빌드/배포/푸시는 하지 않았습니다. 비공개 원문/실제 파일 로딩은 이번 DB 조회 검증에 포함하지 않습니다. R2 인증은 여전히 미설정이며 소설 개발 모드의 로컬 Markdown 경로도 유지합니다.


## 후속: 기존 R2 원문 연결과 소설 로컬 편집 보존

사용자가 소설/만화 원문 연결을 요청하면서 소설의 로컬 편집용 개발 코드를 유지하도록 확정했습니다.

- 원본 Mono `.env`에서 기존 account/key/bucket/endpoint 항목만 새 Mono `.env.local`에 적용했습니다. endpoint 별칭은 기존 storage가 지원하는 `R2_ENDPOINT`로 연결했습니다. DB·독자/관리자 인증·공개 주소·앨범아트 대상 등 나머지 설정은 보존했습니다. 관리자/Loud에는 R2 키를 추가하지 않았습니다.
- Mono 서버만 같은 3100 포트로 재시작했습니다. DB 데이터·R2 객체/접근 정책·DNS·원본 프로젝트는 변경하지 않았습니다.
- NovelReader 개발 분기와 렌더러 코드는 그대로입니다. 개발은 `/novel/{id}.md`, 운영은 기존 `/api/content/novels/{id}`를 사용합니다. 원본 `public/novel`의 Markdown 4개를 새 앱의 같은 위치에 바이트 동일하게 복사했고, 대상의 기존 파일은 덮어쓰지 않는 방식으로 처리했습니다. 로컬 원고와 비밀값은 Git에서 제외됩니다.
- 읽기 검사: 공개 소설 R2 API 200·Markdown 본문/`private, no-store`, 보호 소설 비로그인 401. 만화 3편의 목록 200(66/58/55페이지)와 각 첫 이미지 200·image Content-Type·비어 있지 않은 본문을 확인했습니다.
- 로컬 Markdown 4개 모두 정적 경로 200·파일과 SHA-256 일치. `npm run check:ui`로 소설 소스/스타일 보존 검사를 통과했습니다. 런타임 코드 변경이 없어 lint/typecheck는 반복하지 않았습니다.
- 만화 전체 이미지/모바일·인증된 보호 소설 본문·실제 편집 후 표시 등 전체 사용자 QA를 마친 것은 아닙니다. 업로드/삭제·앨범아트 쓰기·운영 DB 수정·빌드·배포·푸시는 하지 않았습니다.
