# 4단계 앨범아트 연결·검증·전환 절차

2026-10-20 기준 **사용자 QA에서 앨범아트 승인, 운영 36곡 고해상도 키 전환 및 기존 배포 호환·캐시 검증 완료**입니다. 새 모노레포의 운영 배포는 사용자가 진행합니다. 아래 초기 수집/연결 기록과 마지막 실제 전환 기록을 구분하세요.

## 준비된 구성

```text
adminasobi 기존 업로드 API
  → packages/storage: 40MP/정지 JPG·PNG·WebP 검증(통합 관리자 바이트 상한 해제)
  → 원본 픽셀 크기를 유지한 WebP(통합 관리자 3MiB 상한 해제)
  → 앨범아트 전용 R2 버킷에 새 키 업로드
  → 기존 DB 조건부 교체 / 실패 시 새 객체 정리
  → 기존 서버 캐시가 있는 Mono에만 무효화 알림

세 앱의 얇은 adapter
  → packages/ui AlbumArtwork
  → packages/content-core getAlbumArtUrl
  → https://assets.envifloor.uk/cdn-cgi/image/width=200,.../albumart/0/<새 파일>.webp
  → 전용 공개 R2 버킷
```

사용자는 **같은 Cloudflare 계정**임을 확인하고 `assets.envifloor.uk` + 새 `asobi-album-art` 버킷 + 커버만 공개 + Images Free 활성화를 승인했습니다. 실제 APAC/Standard 버킷과 TLS 최소 1.2 커스텀 도메인을 생성했고 Cloudflare 화면의 활성 상태와 공개 HTTP 응답을 확인했습니다. 기존 `*.envifloor.uk` 와일드카드 DNS는 유지되며 `assets`에 새 CNAME만 추가했습니다. `r2.dev`·유료 플랜은 활성화하지 않았습니다. 기존 비공개 버킷 공개 설정도 변경하지 않았습니다.

- UI는 원래 두 앱의 표시/실패 처리와 blob 미리보기를 공용 컴포넌트로 추출했습니다. 명시적 CDN `srcset`을 그대로 전달하기 위해 공용 컴포넌트는 네이티브 `img`를 사용합니다. Next 의존성이나 새 이미지 서버를 추가하지 않았습니다.
- 크기 후보는 **200/400/800/1200/1600px 다섯 개**, 품질 85, format=auto, fit=scale-down입니다. **세 앱 사이드바는 사용자 요청으로 `requestWidth={200}`을 지정해 srcset 없이 200px만 요청합니다.** 그 외 화면은 브라우저가 실제 크기와 DPR로 한 후보를 고릅니다. 가령 120px 미리보기의 2×는 400px 후보입니다. 모든 후보가 즉시 요청되는 것은 아닙니다.
- `sizes`는 현재 고정 표시 크기입니다. 향후 반응형 큰 화면이 생기면 호출부에 맞게 확장하고 실제 표시 폭과 일치시키세요. 1600px보다 큰 요청은 현재 1600px로 제한됩니다.
- 파일 키 검증은 `albumart/<0 포함 정수 ID>/<hex 또는 UUID>.webp`입니다. 소설·만화 경로·외부 URL·경로 이동 문자열은 공용 이미지 주소로 만들지 않습니다.
- CDN 이미지를 Vercel `/_next/image`로 다시 최적화하지 않습니다. `blob:` 미리보기는 CDN에 보내지 않습니다. 이미지 실패는 기존 empty.svg/디스크 아이콘을 사용합니다. 변환 실패 때 수 MB 원본으로 자동 redirect하지 않습니다.
- 환경변수를 비워 두면 기존 Mono API/정적 파일·Loud 디스크 fallback이 유지됩니다. Mono도 공용 네이티브 표시를 쓰므로 이전 `/_next/image` 경유는 제거됐습니다. **독립 주소 검증 전 운영에 고해상도 업로드부터 먼저 적용하지 마세요.**

## 환경변수와 버킷 경계

세 앱의 공개 환경변수는 아래와 같습니다. `.env.example`과 로컬 `.env.local`의 공개 읽기 값에 적용했습니다. 운영 Vercel 환경변수/배포는 건드리지 않았습니다. 후속 사용자 요청에 따라 로컬 Mono/Admin은 기존 R2 인증과 전용 앨범아트 버킷을 사용합니다. 환경별 별도 자원을 요구하지 않으며 비밀값은 Git 제외 파일에만 둡니다. asset 주소만 있고 전용 쓰기 버킷이 없으면 업로드는 의도적으로 거부됩니다.

```dotenv
NEXT_PUBLIC_ASSET_BASE_URL=https://assets.envifloor.uk
NEXT_PUBLIC_ASSET_TRANSFORMS=true
```

서버에서 파일을 읽거나 쓰는 **Mono와 새 관리자**에는 아래 값을 함께 설정합니다. 기존 Mono 관리자 쓰기가 남아 있는 동안에도 동일 대상이어야 합니다.

```dotenv
R2_ALBUM_ART_BUCKET_NAME=asobi-album-art
# R2_BUCKET_NAME은 기존 비공개 소설/만화 버킷 값을 유지
```

공용 storage의 기존 클라이언트와 get/put/delete를 재사용하며, 앨범아트 호출만 명시적으로 전용 버킷을 전달합니다. 소설·만화 읽기/목록은 원래 기본 버킷 그대로입니다. 전용 버킷과 비공개 버킷이 같거나, 공개 asset 주소만 설정하고 전용 버킷을 빠뜨리면 오류로 막습니다. 이 검사는 **Cloudflare의 실제 버킷 공개 여부나 IAM 설정까지 확인하지는 않습니다.**

키는 DB에 그대로 저장하고 호스트·비밀값을 넣지 않습니다. 관리자 주소가 공개 이미지 URL에 포함되지 않습니다. `NEXT_PUBLIC_*`는 빌드 시 반영되므로 추후 배포 시 세 앱의 값을 함께 확인해야 합니다. 단순 런타임 서버 재시작만으로 공개 클라이언트 설정이 바뀐다고 가정하지 마세요.

## Cloudflare 현행 제약과 승인 범위

- R2 커스텀 도메인은 버킷과 **같은 계정에 추가된 zone**이어야 합니다. 같은 계정인지 먼저 확인하고 기존 DNS 기록과 충돌을 점검합니다. `r2.dev`는 운영 주소로 쓰지 않습니다. [R2 공식 문서](https://developers.cloudflare.com/r2/buckets/public-buckets/)
- 커스텀 도메인 연결과 이미지 변환 활성화는 별도 작업입니다. 해당 zone에서 Images 변환과 자신의 이미지 origin만 허용하고 URL 인터페이스를 확인합니다. [변환 옵션](https://developers.cloudflare.com/images/optimization/features/), [원본 허용 범위](https://developers.cloudflare.com/images/optimization/transformations/sources/)
- Images Free는 현재 월 5,000개 고유 변환입니다. 같은 원본/크기 조합의 반복 요청은 한 조합으로 세며, 초과하면 새 변환은 9422 오류가 납니다. Free 초과분이 자동 청구되지는 않습니다. 현재 36곡×5크기는 180조합이지만, 교체된 파일과 추가 이미지도 별도 조합이며 계정의 다른 사용량까지 보장하는 계산은 아닙니다. R2 저장/요청 사용량은 별도로 확인합니다. [가격 공식 문서](https://developers.cloudflare.com/images/pricing/)
- 새 버킷 생성·객체 복사/업로드·도메인 연결·공개 접근·Images Free 활성화의 구체적 대상을 확인하고 승인된 작업만 실행합니다. 유료 전환·운영 DB 키 교체·이전 파일 삭제를 묶어서 승인받은 것으로 해석하지 않습니다.

## 수집 결과와 적용 순서

[수집본 안내](../assets/album-art/README.md)와 [manifest](../assets/album-art/manifest.json)가 파일/출처의 원본입니다. 공개 목록의 ID 0–35 총 36곡, 모두 3000×3000 JPEG와 동일 크기 WebP를 준비했습니다. Orion은 사용자 지정 THE BOOK for,입니다. 기존 정적 파일의 실측은 200px 세 개부터 최대 1080px까지 혼재했으며, 운영 프록시의 ID 0 응답은 3,734B의 작은 파일이었습니다. 수집본은 전용 버킷에 새 키로 올렸고 공개 URL을 검증했습니다. 초기 수집 당시 운영 DB/앱 배포는 바꾸지 않았으며, 후속 승인된 DB 전환 결과는 마지막 절에 있습니다.

1. **기존 주소를 보존하는 버킷 분리부터** 합니다. 최신 활성 곡의 DB 키 목록을 읽고 `albumart/` 안의 현재 연결 객체만 전용 버킷에 **같은 키로 복사**합니다. 소설/만화나 버킷 전체 sync를 하지 않습니다. 원본 객체는 그대로 둡니다. 현재 public 목록 snapshot을 최신 DB의 대용으로 쓰지 않습니다.
2. 각 객체의 source/target 바이트 수·직접 계산한 SHA-256·Content-Type을 비교합니다. ETag를 무조건 파일 해시로 해석하지 마세요. 복사 중 곡의 키가 바뀌었으면 최신 키를 다시 확인하고 누락을 보완합니다.
3. 전용 검증 대상에서 커스텀 도메인·변환·캐시를 확인한 뒤 두 서버의 전용 버킷 설정과 세 앱의 asset 주소를 맞춥니다. 이 시점의 DB 키는 그대로이므로 고해상도 교체와 분리해서 복구할 수 있습니다. 새 관리자뿐 아니라 남아 있는 Mono 쓰기도 같은 대상으로 맞춥니다.
4. **고해상도 교체는 별도 승인된 운영 작업**으로 진행합니다. manifest의 준비본과 최신 ID/제목을 대조하고, 새 파일 키로 업로드한 뒤 checksum을 확인합니다. 기존 CAS 저장 순서를 사용하거나 동등하게 최신 `album_art_key`를 조건으로 교체합니다. 다른 곡 정보·가사·콜을 덮어쓰지 않습니다. manifest의 `observedKeyAtCollection`이 현재도 같다고 가정하지 않습니다.
5. 기존 Mono 서버 캐시 무효화(Loud는 다음 요청에서 DB 조회) → 실제 목록/상세 이미지 → 교체/실패 정리 → 사용자 QA를 확인합니다. DB 쓰기와 파일 업로드가 성공했다는 이유만으로 CDN 변환/화면 QA까지 완료 처리하지 않습니다.

기존 업로드는 실패 시 새 객체 삭제를 계속 수행합니다. 전용 버킷 설정이 있는 전환 기간에는 **이전 객체 자동 삭제를 보류**합니다. 원본 버킷/이전 키를 보존해 복구할 수 있게 한 것이며, 용량 정리와 공개 중단은 아래 별도 절차를 따릅니다. 전환 설정이 없는 기존 경로는 기존의 성공 후 이전 객체 정리를 유지합니다.

## 캐시·공개 중단·복구

기존 키 검증 프록시는 현재 DB에 연결되지 않은 키를 새 요청에서 거부합니다. 공개 R2/CDN은 이 DB 검사를 하지 않습니다. 이전 커버 URL은 파일이 존재하거나 엣지/브라우저에 캐시돼 있으면 계속 열릴 수 있습니다. 공개 커버만 전용 버킷에 넣으며 비공개 문서/미리보기와 섞지 않습니다. blob 미리보기는 브라우저 안에만 있습니다. 향후 비공개 파일 미리보기가 필요하면 인증 경로로 따로 제공합니다.

일반 교체는 새 키로 캐시를 분리합니다. 공개 중단은 DB 숨김만으로 끝내지 않고 해당 객체/접근을 중단하고 원본 URL과 변환 URL을 함께 purge한 후 새 요청을 검사합니다. 이미 내려받은 파일이나 브라우저의 immutable 캐시까지 회수된다고 보장하지 마세요. 긴급 차단은 도메인 접근 정책도 고려하되 다른 커버에 미치는 범위를 먼저 확인합니다.

복구는 변경 전 키 목록·환경변수와 이전 버킷을 기준으로 진행합니다. 먼저 양쪽에 필요한 객체가 있는지 확인하고 DB를 조건부로 복구한 후 캐시를 갱신합니다. 전환 후 새 키를 기존 버킷에 복사하지 않은 상태에서 환경변수만 원래대로 바꾸면 이미지가 누락됩니다. 양쪽 버킷을 자동으로 뒤져 읽는 경로는 만들지 않았습니다.

## 실제 검사 결과와 남은 검사

| 요청    | 첫 응답 |    전체 | 전송량 | Vercel 캐시 |
| ------- | ------: | ------: | -----: | ----------- |
| 첫 번째 | 3,005ms | 3,008ms | 3,734B | MISS        |
| 두 번째 |    68ms |    69ms | 3,734B | HIT         |

두 응답 모두 `public, max-age=31536000, immutable`이었습니다. 한 지역/파일의 2회 표본이며, MISS 구간의 DB·함수 시작·R2 비용을 따로 계측한 결과는 아닙니다. 작은 파일에서도 차이가 커서 첫 요청의 서버 경로를 줄이는 것이 유효할 수 있지만, 무료 플랜의 고정 한계나 CDN의 예상 응답 시간으로 단정하지 않습니다.

**남음:** 사용자 운영 앱 환경변수/배포 전환, 관리자 저장 API의 실제 R2+CAS+실패 정리 통합 QA, 공개 중단·purge, 모바일/DPR/다크모드/실제 선택 미리보기 QA. Free 한도 초과를 실제로 소모하는 실험은 하지 않았습니다. Production build·앱 배포는 실행하지 않았습니다. 후속 승인된 DB 키 전환은 마지막 절에 기록합니다.

## 승인 후 실제 외부 실행 결과

- R2: `asobi-album-art` 생성, 현재 공개 목록에서 수집한 기존 키 36개를 같은 경로로 복사, 새 3000px WebP 36개 업로드. 총 72개 모두 S3로 다시 읽어 크기·SHA-256·Content-Type을 대조했습니다. 원본은 삭제하지 않았고 기존 키가 존재하면서 내용이 다르면 덮어쓰지 않고 실패하도록 했습니다. 복사 시점에 DB는 읽거나 변경하지 않았으므로 운영 전환 직전 최신 DB/공개 목록의 차이는 다시 확인해야 합니다.
- Images: envifloor.uk zone 활성화, 지정된 원본에 `assets.envifloor.uk`의 `/albumart` 추가 후 저장 완료 메시지 확인. 기존 기본 `envifloor.uk` 전체 경로 항목은 유지했습니다. 해당 기본 항목 삭제 시도는 자동 승인 검토가 다른 사용처 중단 우려로 거절했으므로 삭제하지 않았고, 전용 원본을 추가하는 안전한 대안으로 연결을 완료했습니다. 루트 항목 정리는 이번 작업에 필요하지 않으며 별도 결정 없이 재시도하지 마세요.
- 도메인: `assets.envifloor.uk` 활성/Access 사용됨/TLS 1.2 확인. 초기화 중 잠시 원본 403·변환 9408을 반환했으나 활성화 후 정상 200으로 바뀌었습니다. 오류를 피하려고 인증서 검증이나 보안 설정을 낮추지 않았습니다.
- HTTP: 고해상도 원본 36개 모두 HEAD 200·image/webp·크기 일치, ID 0 원본 GET 3000×3000·SHA-256 일치, ID 0의 5개 크기와 재요청, ID 35의 400px을 실제 디코딩했습니다. 기존 키 ID 0도 200 응답/200px을 확인했습니다. 없는 변환 원본은 404이며 원본으로 자동 redirect하지 않습니다.

첫 측정 표본은 같은 실행 환경/특정 파일에 한정됩니다. `format=auto`와 AVIF 수용 헤더를 사용했으며 실제 크기를 디코딩했습니다. 재검사에서 Content-Type=image/avif와 immutable 1년 헤더도 확인했습니다. 다만 나중 재검사 첫 요청에는 다시 MISS가 나타났으므로 모든 후속 요청이 항상 HIT가 된다고 보장하지 않습니다. 엣지별 캐시 차이는 별도 계측하지 않았습니다. 아래 용량은 로컬 WebP 예측값과 다릅니다.

## 사용자 승인 후 운영 키 전환 완료

사용자는 앨범아트 QA를 승인했고, 시점 확인에서 **지금 전환 — 현재 운영 배포의 호환 경로와 캐시까지 처리하기**를 선택했습니다. 이 작업은 앱 배포나 파일 삭제 승인이 아닙니다.

- 최신 운영 DB 36곡의 ID/제목/기존 키를 manifest와 대조했습니다. 수집 이후 키 변경이 없었습니다.
- 공개 `asobi-album-art`의 새 3000×3000 WebP 36개를 로컬 준비본 SHA-256/Content-Type과 대조했습니다. CDN의 200px 응답 36개를 실제 디코딩했습니다.
- 기존 비공개 `monoasobi-contents`에는 **같은 새 키에 200×200 호환본 36개**를 추가했습니다. 기존 운영 Mono는 여전히 이 버킷을 읽으므로 배포 전에도 새 키가 열립니다. 두 버킷의 같은 키에 크기가 다른 것은 전환 기간의 의도된 호환 조치입니다. 기존 객체 덮어쓰기/삭제나 버킷 공개 변경은 하지 않았습니다.
- 준비 중 DB가 바뀌지 않았는지 쓰기 트랜잭션 안에서 재검사하고 각 행의 기존 키·updated_at을 조건으로 **album_art_key와 updated_at만** 교체했습니다. 실패 시 트랜잭션 롤백, 캐시 알림 실패 시 이전 키로 조건부 복구하도록 했습니다. 실제 전환은 36건 모두 성공했습니다.
- 기존 운영 Mono에는 새 무효화 전용 API가 없어, 기존 관리자 인증 후 **첫 곡의 최신 값을 그대로 재저장**해 기존 public-catalog 태그를 무효화했습니다. 이 한 곡의 updated_at이 한 번 더 바뀌며 다른 필드는 보존됩니다. 전체 변경 전후 비교에서도 키/시각 외 필드 변화는 없었습니다.
- **기존 운영 프록시 36개 모두 HTTP 200/200×200**, 운영 홈 200과 새 키 36개 노출을 확인했습니다. 로컬 Mono/Loud 홈 200 및 새 키 36개, 인증된 Admin 상세 200·새 키 반영을 확인했습니다. 열린 화면을 강제로 바꾸지는 않습니다.
- 로컬 Mono/Admin의 전용 버킷을 명시하고 Admin에 기존 R2 인증을 연결했습니다. 원본 checkout과 Vercel 환경변수는 바꾸지 않았습니다.

실행 도구는 `scripts/activate-album-art.mjs`이며 기본 실행은 DB 읽기 계획만 출력하고 `--apply`일 때만 전환합니다. 기존 storage/libSQL/Sharp를 재사용합니다. 실행은 `node --conditions=react-server --import tsx ...` 형태이며 현재 작업용 secret loader는 무시된 `.local/run-artwork-activation.mjs`에 있습니다. loader는 환경 파일을 프로세스에서만 읽으며 값을 출력하지 않습니다. 이 전환을 install/dev/build에 연결하거나 자동 반복 실행하지 마세요. 과거 운영 배포가 종료되면 legacy API를 전제로 한 재실행도 하지 않습니다.

변경 전후 백업은 Git 제외 `.backups/album-art-activation/2026-10-20T11-44-45.102Z/{before,after}.json`에 있습니다. 복구가 필요하면 최신 행이 적용 키를 유지하는지 확인하고 이전 키만 조건부 복구한 뒤 해당 운영 배포의 캐시를 초기화합니다. 가사·콜·곡 정보 전체를 백업으로 덮어쓰지 않습니다. 이후 사용자가 교체한 이미지는 복구 대상에서 제외합니다.

추가 업로드의 구버전 호환본 자동 복제는 구현하지 않습니다. 현재 36곡 전환용 호환만 준비했습니다. 새 배포 완료 전 추가 교체는 피하고 [운영 환경·배포 순서](production-environment.md)를 따르세요. 기존 파일 정리/공개 중단·purge와 관리자 업로드 실패 정리의 실제 통합 QA는 별도입니다.


## 관리자 QA 후속 — 이미지 선택과 크기 제한

사용자 요청으로 통합 관리자 앨범아트를 공통 최상단으로 옮기고 이미지 클릭으로 파일을 선택하게 했습니다. 선택한 새 파일명은 썸네일 오른쪽에 표시하며 별도 파일 선택 행은 없습니다. 새 곡 등록과 곡 상세는 같은 AlbumArtField를 사용합니다.

통합 관리자 UI와 API의 입력/변환 결과 3MB 자체 제한을 해제했습니다. 기존 normalizeAlbumArt에 선택적 maxBytes를 두고 이 경로만 Infinity를 전달합니다. 레거시 Mono의 기본 제한과 집중 검사는 그대로입니다. 포맷/정지 이미지/40MP·원본 비율·R2 CAS/실패 정리는 유지합니다. 호스팅의 HTTP 요청 한도는 별개이며 이 변경이 플랫폼 전송 한도를 늘리지는 않습니다.

입력과 결과 모두 3MiB 초과인 실제 PNG→WebP 검사 통과, 잘못된 대용량 입력은 관리자 API에서 400으로 거부됨을 확인했습니다. 실제 운영 R2 업로드·DB 이미지 키 변경 테스트는 하지 않았습니다.
